# История разработки Aurora

Этот документ — короткий живой журнал проекта. Он фиксирует не каждую правку, а завершённые этапы, принятые
архитектурные решения, отменённые направления и следующую проверяемую цель. После каждого законченного этапа журнал
обновляется тем же коммитом.

## Текущее состояние — 23 сентября 2026

- Aurora работает как локальный живой справочник Minecraft, а не как автономный компаньон или NPC.
- Пользовательский мод показывает отдельный чат, запускает локальную Ollama и ищет знания во внешних профилях.
- Runtime не читает NEI/JEI, реестры рецептов, дропы или классы установленных модов.
- Профиль `vanilla-1.7.10` содержит 324 статьи: 322 статьи старого формата и 2 эталонные статьи schema v2.
- Полный реестр Minecraft 1.7.10 содержит 171 блок; подробно обработано 2, ожидают обработки 169.
- Обычная сборка проверяет формат статей, уникальность ID, ссылки на источники и число статей в manifest.
- Актуальная версия профиля в исходниках — `0.3.0`. Публичный каталог всё ещё указывает `0.2.0`; новый профиль пока
  не опубликован как релиз.

## Хронология

### 21 сентября — рабочий игровой MVP

- Создан клиентский мод Forge 1.7.10 с подключением к локальной Ollama.
- Реализованы установка runtime и модели внутри экземпляра Minecraft, их автоматический запуск и остановка.
- Создан двухвкладочный интерфейс «Игровой чат / Аврора», всплывающие сообщения и приватная отправка вопросов.
- Знания отделены от JAR в версионированные внешние профили.
- Добавлены безопасная установка профиля и автоматическая проверка онлайн-каталога.

### 22 сентября — первый каталог знаний

- Сформирован слой рецептов крафта и печи Minecraft 1.7.10.
- Исправлены обрезанные ответы модели и добавлены первые общие статьи о дропах.
- Выявлено, что одних рецептов недостаточно: модели нужны проверяемые сведения о сущностях и механиках.

### 23 сентября — отказ от runtime-ридеров

- Были опробованы чтение активных рецептов, дропов блоков и MobsInfo прямо во время игры.
- Эксперимент отменён: такой подход связывал Aurora с внутренностями конкретной сборки, усложнял тестирование и не
  давал полноценного объяснительного знания.
- Удалены runtime-ридеры и автономные наблюдатели здоровья, смерти, огня и инвентаря.
- Зафиксирована catalog-first архитектура: инструменты разработки могут изучать игру, пользовательский мод получает
  только готовый проверенный профиль.
- Проведена ревизия безопасности установки, обновления, ZIP-архивов, фоновых очередей и prompt boundaries.
- Введена schema v2: отдельные факты, условия, связи и источники вместо одного неструктурированного абзаца.
- Добавлен автоматический валидатор профиля и две эталонные статьи: камень и алмазная руда.
- Из реального реестра Minecraft 1.7.10 построен контрольный перечень всех 171 блоков.
- Обнаружено, что сторонний набор `minecraft-data/pc/1.7` содержит примесь блоков 1.8; первичным источником состава
  версии оставлен реестр игры.

## Решения, которые нельзя случайно отменить

1. Факты не встраиваются в JAR и не запекаются в модель Ollama.
2. Aurora не обучается на действиях игрока и не изменяет базу знаний во время игры.
3. Пользовательский runtime не исследует установленные моды; сбор данных разрешён только офлайн-инструментам
   подготовки каталога.
4. Каждая статья относится к точной версии игры или модпака.
5. Каждый важный факт schema v2 имеет источник; спорные числа проверяются по коду версии или ручным тестом.
6. Сторонние базы используются для сверки, но не импортируются вслепую.
7. GTNH получает отдельный профиль только после стабилизации vanilla 1.7.10.

## Параллельные направления

Работа делится по непересекающимся зонам, чтобы несколько агентов не редактировали одни файлы одновременно:

- **Блоки A, ID 0–43:** природные блоки, руды, растения и ранние механизмы; ID 1 уже готов.
- **Блоки B, ID 44–87:** строительство, рабочие станции, транспорт и базовый redstone; ID 56 уже готов.
- **Блоки C, ID 88–131:** Незер, Энд, фермерство, зельеварение и порталы.
- **Блоки D, ID 132–175:** поздний redstone, кварц и добавленные в 1.7 блоки; ID 165–169 в версии отсутствуют.
- **QA и интеграция:** источники, тесты релевантности, дубликаты, manifest, coverage и полная сборка.

Контент-агенты создают только новые JSON своего диапазона и не меняют manifest, coverage, README, документацию или
сборку. Интегратор единолично обновляет центральные файлы. Интеграция выполняется партиями по 10–15 блоков. Перед
слиянием каждая партия проходит валидатор, редакторскую проверку источников, полную сборку и обновление coverage.
Изменение schema или общих runtime-классов не выполняется параллельно без отдельного согласования.

## Следующая цель

Подготовить первую проверенную партию природных блоков и руд, довести coverage блоков с `2/171` до `12/171`, затем
проверить ответы на заранее зафиксированном наборе вопросов. После этого можно увеличивать партии, не ухудшая
точность.
